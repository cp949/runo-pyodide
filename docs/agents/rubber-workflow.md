# rubber-workflow

한 덩어리의 작업을 DELTA 단위로 나눠 실행하는 절차. "로드맵"이라는 단어가 무엇을 할지 정리한
문서(`ROADMAP.md`)와 어떻게 실행할지 정하는 절차 양쪽에서 다른 뜻으로 쓰이면 혼란스러워서, 이
저장소에서는 실행 절차를 "rubber-workflow"라고 부른다. DELTA를 미리 다 계획하지 않고 작업 중
발견에 따라 그때그때 추가·분할하는 탄력성("고무")이 핵심이다.

## 진입 경로

다음 둘 중 하나로 시작한다. **모든 rubber-workflow 작업을 `ROADMAP.md`에 먼저 등록해야
하는 것은 아니다** — `ROADMAP.md`는 여러 단계로 나눠 진행하는 큰 작업에만 쓴다. 일회성
작업(당장 처리하는 큰 버그 수정·리팩터링 등, 이후 단계가 이어지지 않는 작업)은 ROADMAP
항목 없이 브레인스토밍 경로로 바로 시작한다.

- **브레인스토밍**: 사용자와 논의해 확정한 작업(브레인스토밍 스킬의 설계 승인 등). 관련
  ROADMAP 항목이 없다. 일회성 작업은 대부분 이 경로로 시작한다.
- **ROADMAP.md 항목**: 루트 `ROADMAP.md`의 항목 하나를 실행. 여러 단계로 나눠 진행할
  정도로 큰 작업만 여기 등록한다.

둘 다 아래 절차는 동일하다. ROADMAP.md 항목에서 시작했으면 "마무리"에서 `ROADMAP.md`도
갱신한다.

## 언제 쓰나

한 번에 끝내기엔 크다고 판단되는 작업. 사소한 작업(문서 한 파일 수정, 설정 한 줄 변경)에는
쓰지 않는다 — 그런 작업은 바로 한다.

## 작업공간

`_works/<yyyyMMdd>-NN-<제목>/` (`_works/`는 `.gitignore` 대상). `_works/` 바로 아래에서
`yyyyMMdd-NN-` 접두어가 붙은 폴더만 작업 폴더로 취급하고, 다른 항목은 작업과 무관한 자료이므로
건드리지 않는다. 완료된 작업 폴더는 `_works/_completed/`로 옮긴다(아래 "마무리" 참고) — 진행
중인 작업 폴더만 `_works/` 바로 아래에 있다.

```text
_works/20260921-01-example-task/
  _meta.md               # 작업 브랜치·관련 ROADMAP 항목·상태 — 다른 에이전트가 이어받기 위한 최소 정보
  checklist.md            # 목표·범위·DELTA 목록·최종 완료 조건
  DELTA-01.md
  DELTA-02.md
  DELTA-02a.md            # 작업 중 분할/추가된 것
  pending-traps/
    01.md ...
  pending-issues/
    01.md ...
```

## 시작

작업 폴더를 만들고 `_meta.md`, `checklist.md`를 순서대로 작성한 뒤 브랜치를 만든다.

```markdown
---
작업 브랜치: example-task
착수 커밋: <git rev-parse HEAD 값>
관련 ROADMAP 항목: 없음 # ROADMAP.md 항목에서 시작했으면 해당 항목
상태: 진행중
---
```

`_meta.md`는 이 네 필드만 가진다. **진행 로그를 쓰지 않는다** — 판단이 필요했던 지점은
해당 `DELTA-NN.md`의 "## 결정" 절에 남긴다(아래 "DELTA-NN.md 형식" 참고). 상태는 `진행중`
/ `완료` 둘 뿐이고, 다른 에이전트가 이 작업 폴더를 이어받아도 되는지 판정하는 용도로만
쓴다.

`_meta.md` 작성 후 `git switch -c <작업 브랜치> dev`로 브랜치를 만든다. 브랜치 생성 직후
`git rev-parse HEAD`로 착수 커밋 해시를 얻어 `_meta.md`의 `착수 커밋`에 적는다. 전체 브랜치
리뷰(아래 "리뷰")가 이 해시를 리뷰 범위의 시작점으로 쓴다 — `dev`가 작업 중 앞서 나가거나
브랜치와 무관한 푸시하지 않은 커밋이 있어도 리뷰 대상이 이 작업에서 만든 커밋만으로
고정된다.

### 설계 전제 확인 (2026-09-26 사용자 확정)

브레인스토밍 `design.md`·checklist의 규칙이 기대는 전제는 **계획 단계에서 코드로 확인**한다. 구현
뒤 리뷰에서 전제가 틀린 것이 드러나면 코드·시험·문서를 전부 다시 고쳐야 한다(RD-028: `tail()`이
`\r\n` 뒤 빈 값이 된다는 전제가 틀려 병합 뒤 DELTA 2개, 약 40분 재작업).

- 규칙이 쓰는 함수·값(예: `io.sinks.tail()`)의 실제 의미를 구현 파일에서 읽고, `design.md` 사실 절에
  `파일:줄` 근거를 적는다. 근거 없는 서술은 "가설"로 적는다.
- 같은 판정을 이미 하는 코드가 있는지 grep하고 명령·결과를 적는다(RD-028: `sinks.ts`가 이미
  `leavesVisibleText`로 같은 판정을 하고 있었다).
- checklist "착수 전 읽기"에 설계 문서뿐 아니라 위 구현 파일을 넣는다.

## checklist.md

작업 시작 시 작성.

```markdown
# <제목> 완료 체크리스트

- 목표: ...
- 범위(포함/제외): ...
- 관련 ROADMAP 항목: ROADMAP.md#<항목> (브레인스토밍에서 시작했으면 생략)
- 착수 전 읽기: <설계 절> + <규칙이 기대는 구현 파일> (위 "설계 전제 확인")

## DELTA 목록

- [ ] DELTA-01: <한 줄 스코프>
- [ ] DELTA-02: <한 줄 스코프>

## 완료 조건

- [ ] 조건 1
- [ ] 조건 2
```

DELTA 목록은 **확정이 아니다** — 작업 중 언제든 추가·분할한다. 빠진 게 발견되면 바로
목록에 한 줄 추가하고 계속 진행한다(별도 승인 없이). 기존 DELTA를 쪼개야 하면
`DELTA-01a`, `DELTA-01b` 형태로 추가한다(뒤 번호를 밀지 않음).

완료 조건은 **필수 통과 / 허용 편차 / 제외**를 구분해 적는다. 이전 구현이나 다른 RD의
하니스·셀 정의를 옮겨 오면 셀별 예외(`allowOurFrames`, 트레이스백 개수 허용 등)와
`docs/design/10-parity-deviations.md`의 등록 편차를 시나리오마다 대조해, 편차에 해당하는 셀은
처음부터 "허용 편차"에 둔다. 편차가 등록돼 있는데 "전부 통과"를 요구하는 완료 조건을 만들지
않는다.

## 검증 실행 예산 (e2e 최소화)

브라우저 e2e와 반복 측정은 1회에 수 분~수십 분 걸린다(전체 `e2e:baseline` 약 8분 이상, node 통계
5분 이상). 검증은 아래 4단계로 나누고, **L2·L3은 사용자가 지시할 때만 돌린다**(2026-09-24 사용자
확정). 검증 방법은 **계획 단계에서** 가장 싼 단계부터 고르고 실행 횟수를 적는다.

| 단계 | 수단                                                                                                                                 | 언제                                                                              |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| L0   | 브라우저 없는 검증: `pnpm check-types`·`lint`·`test`·`build`, 함수 하니스(가짜 입력), `pnpm --filter demo e2e:check`(`node --check`) | 모든 변경. 에이전트가 스스로 돌린다                                               |
| L1   | 개별 e2e 스크립트(`pnpm --filter demo e2e:<이름>`, `ONLY=`·`N=` 축소) — 변경 영역에 해당하는 스크립트만                              | 브라우저 동작을 바꾼 DELTA. 계획서에 스크립트·횟수를 적고 그 안에서 스스로 돌린다 |
| L2   | 전체 `pnpm --filter demo e2e:baseline`                                                                                               | **사용자 지시 때만**. 계획서 예산은 0으로 적는다                                  |
| L3   | `e2e:measure`, `node/` 통계, 조건 스윕, 반복 측정(N≥10), 브라우저 양성 대조 여러 건                                                  | **사용자 지시 때만**                                                              |

- RD·이슈 완료는 L0 + L1로 판정한다. 기대값이 바뀐 스크립트는 L1 결과로 `apps/demo/e2e/BASELINE.md`의
  해당 행만 갱신한다. 전체 기준선 대조(L2)는 사용자가 지시할 때 한다.
- L2·L3이 필요하다고 판단되면 실행하지 말고 멈춰서 이유·대상·예상 시간을 알리고 지시를 기다린다.
- L1 안에서 고르는 순서:
  1. 이미 있는 로그·결과 파일·이전 DELTA `verify/` 기록 — RED를 재현하지 않고 인용한다.
  2. L0로 확인되면 브라우저를 쓰지 않는다. `run.mjs`·`lib.mjs` 같은 집계/도구 변경은 판정 대상
     스크립트 동작이 안 바뀌면 L0에서 끝낸다.
  3. 개별 스크립트 1개, `ONLY=`로 대상 절만, 반복은 `N=` 최소치.
- 수정 후 재확인은 실패한 스크립트(가능하면 실패한 절)만 다시 돌린다.
- 반복 횟수 N은 완료 조건 최소치만 쓴다. 변이 검사·양성 대조는 L0(단위 시험)에서 먼저 하고, 브라우저
  양성 대조는 대상 스크립트 1개·대상 절만 L1 예산 안에서 한다.
- 계획한 L1 횟수를 넘어야 하면 실행 전에 멈추고 이유·추가 횟수·예상 시간을 알려 확인받는다.
- e2e 스크립트를 새로 쓰거나 고칠 때는 시간 판정 규칙(`docs/design/09-testing.md` 9.7)을 따른다.

### L0 반복 범위 (2026-09-26 사용자 확정)

RD-028에서 L0 실행만 약 20분이 들었다(repl 패키지 전체 시험 20회). 대부분 변경과 무관한 실제
pyodide 시험(`worker/boot`·`console-compat` 등, 1회 약 38초)이었다.

- DELTA 진행 중(RED·GREEN·변이 검사·기존 시험 전환)에는 변경 파일과 그 시험 파일만 돌린다:
  `cd packages/<패키지> && pnpm exec vitest run <파일 일부 이름...>`. `pnpm --filter <패키지> test -- <이름>`은
  필터가 적용되지 않아 패키지 전체를 돌린다(`09-testing.md` 9.1).
- repl 패키지 넓은 확인은 `pnpm --filter @cp949/runo-pyodide-repl test:fast`(실제 pyodide 시험 제외, 약 5초)를
  쓴다. `src/worker/**`·pyodide 쪽 코드를 바꾼 DELTA만 패키지 전체 `test`를 쓴다.
- 루트 전체 L0(`check-types`·`lint`·`test`·`build`)는 **DELTA의 마지막 코드 변경 뒤 1회**만 돌린다.
  결과 기록·커밋만 한 뒤에는 다시 돌리지 않는다. 문서·주석만 바꾼 DELTA는 `check-types`·`lint`만 돌린다.
- 이미 `deferred` 라벨로 등록된 간헐 실패 이슈가 있으면 그 시험만 1회 단독 재실행해 판정한다. `git
  stash`로 변경 전 코드에서 재현하거나 원인을 조사하지 않는다.
- 변이 검사는 변이 하나마다 "대상 파일을 스크래치에 복사 → 변이 적용 → 대상 시험 파일만 실행 → 복사본으로
  되돌림"을 한 Bash 호출로 묶는다. `git checkout -- <파일>`로 되돌리지 않는다(커밋 전 구현까지 지운다).
  원복은 마지막에 `git diff --stat`으로 한 번 확인한다.

## DELTA-NN.md 형식

```markdown
# DELTA-NN <한 줄 제목>

## 계획

- 목적:
- 변경 대상:
- 완료 기준(검증 방법 포함):
- 검증 실행 예산: <L1 개별 스크립트·`ONLY=`·반복 횟수, 예상 시간. L2·L3은 0(사용자 지시 때만)>

## 결과

<!-- 비어 있으면 이 DELTA는 아직 진행 중(또는 미시작)이라는 뜻 -->

- 상태:
- 검증 근거:
- 발견/처리:
- 남은 위험:

## 결정

<!-- 판단이 필요했던 지점만, 있을 때만 추가. append-only -->
```

"## 결정"은 이 DELTA를 진행하며 애매한 것을 임의로 골라야 했던 지점을 남긴다 — 주제,
결정, 근거, 틀렸을 때 비용을 적는다. 없으면 절 자체를 생략한다.

### 결과 기록 분량 (2026-09-26 사용자 확정)

"## 결과"는 다음 에이전트가 이어받고 사용자가 판정하는 데 필요한 것만 적는다. RD-028은 코드 변경
약 110줄에 DELTA 기록이 약 90KB였고, 기록 자체의 오류(시험 수 혼용·오타·줄번호)가 리뷰에서 지적돼
기록만 고치는 DELTA가 따로 생겼다.

- 검증 근거는 명령과 결과 한 줄(통과/실패, 실패면 시험 제목·에러 첫 줄)이다. 출력·시험 개수·
  소요 시간을 옮겨 적지 않는다(L1 첫 실행 시간처럼 계획이 요구한 값만 적는다).
- 줄번호를 적지 않는다. 위치는 파일 경로와 함수·시험 이름으로 적는다.
- 규칙 표 → 시험 대응 표를 결과에 쓰지 않는다. 규칙 표 행에 ID(예: `R3`)를 붙이고 시험 제목에 넣어
  `grep -n "\[R3\]" <시험 파일>`로 확인한다. checklist 완료 조건도 이 grep 명령으로 적는다.
- 앞 DELTA 결과를 다시 옮겨 적지 않는다. 필요하면 "DELTA-02 결과 참고"로 가리킨다.
- `ROADMAP.md` 결과 문단은 성공·예외·후속만 5줄 안팎으로 적는다. DELTA 결과를 복사하지 않는다.

## DELTA 사이클

DELTA 하나 = 계획 → 구현 → 확인 → 정리, 한 번에 끝까지.

1. checklist의 DELTA 목록에서 다음 하나를 고른다(번호 순서 고정 아님).
2. `DELTA-NN.md`를 만들고 "## 계획"에 목적·변경 대상·완료 기준(검증 방법 포함)·검증 실행
   예산을 적는다(위 "검증 실행 예산").
3. 구현한다. 테스트 가능한 부분은 실패(RED) 확인 후 최소 구현으로 통과(GREEN). RED·GREEN은
   가장 싼 검증 수단으로 확인한다 — 전체 e2e로 RED를 재현하지 않는다.
4. 완료 기준을 실제로 확인한다(`pnpm check-types`, `pnpm lint`, `pnpm test`, `pnpm build`
   중 범위에 해당하는 명령의 실행 결과, 브라우저 확인 등 — 근거를 남긴다).
5. `DELTA-NN.md`의 "## 결과"에 상태·검증 근거·발견한 것·남은 위험을 적는다.
6. 함정/후속 작업을 발견하면 `pending-traps/`, `pending-issues/`에 바로 적어둔다 — 승격
   판단은 지금 하지 않는다. 단, 발견이 뒤 DELTA의 계획 문구나 checklist의 완료 조건과
   모순되면 그 문구를 지금 고친다(뒤 DELTA에서 재판단하도록 미루지 않는다). 완료 조건을
   약하게 만드는 변경은 아래 "작업 분할과 완료 조건 변경"을 따른다.
7. checklist의 DELTA 체크박스와 완료 조건을 갱신한다.
8. 작업 브랜치에 커밋한다(아래 "브랜치와 병합" — 자유롭게, 매번 확인받지 않음).
9. 다음 DELTA를 고른다. 목록이 비면 완료 조건을 재확인하고, 다 채웠으면 마무리한다.

### 작업 분할과 완료 조건 변경

- 기존 범위를 `DELTA-06a`·`06b`처럼 나누는 것은 실행상의 선택이다. 별도 승인 없이 한다.
- 완료 조건을 바꾸는 것(실패한 셀을 편차로 제외, 판정선 완화, 지원 범위 추가)은 별도
  결정이다. 해당 DELTA의 "## 결정"에 주제·바꾼 문구·근거를 적고 **사용자 확인을 받은 뒤**
  checklist를 고친다. 분할한 DELTA 안에서 문서 갱신과 함께 조용히 처리하지 않는다.
- checklist의 "멈추는 지점"이 발동했으면 자체 해결(측정법 변경, 스크립트 수정) 여부와
  무관하게 "## 결정"에 발동 사실·1차 결과·해결 근거를 적는다.
- 완료 보고(checklist 완료 조건, `ROADMAP.md` 완료 기준)는 성공과 예외를 함께 적는다.
  예: 복귀 240/240, 형식 10/12셀, 편차 2셀 수용(근거). 실측으로 원래 요구를 덮어쓰지 않는다.

### 문서 갱신: 규칙은 한 곳에 (2026-09-26 사용자 확정)

동작 규칙(판정 조건·상태표·순서)은 **한 문서의 한 절에만** 정의하고, 다른 설계 문서·CONTEXT·함정
문서·코드 주석은 그 절을 링크로 가리킨다. RD-028의 행 머리 규칙은 11곳에 각각 풀어 써 있어, 판정식 하나를
바꾸자 11곳을 다시 고쳐야 했고 고치다 빠진 7곳 때문에 DELTA가 하나 더 생겼다.

- 정의 위치는 규칙을 소유한 모듈의 설계 절(`docs/design/*`)이다. `CONTEXT.md`에는 용어 정의 한 줄과
  링크만 둔다. 코드 머리 주석은 "규칙: `docs/design/<파일>` <절>"과 코드에서만 보이는 사실만 적는다.
- 문서 DELTA는 계획에 grep 명령을 적어 규칙을 다시 풀어 쓴 곳을 찾고, 새 서술을 더하는 대신 링크로 바꾼다.
- 규칙을 바꾸는 DELTA는 정의 절 1곳과 링크가 깨진 곳만 고친다.

### 리뷰 (서브에이전트 협업 모드, 2026-09-26 사용자 확정)

RD-028에서 DELTA별 리뷰 4회(sonnet)는 전제 오류를 놓쳤고, 병합 뒤 전체 리뷰(opus)가 잡았다. 리뷰는
결함이 생기는 곳에 두고 모델을 맞춘다.

- 규칙·상태 판정·프로토콜을 바꾸는 핵심 로직 DELTA는 구현 직후 opus로 리뷰한다. 리뷰 범위에 규칙이 기대는
  전제(위 "설계 전제 확인")와 같은 판정을 하는 기존 코드와의 일치를 넣는다.
- 기계적 이전(호출자 갱신·시험 셋업 전환)만 한 DELTA는 sonnet 리뷰 1회, 문서·주석만 바꾼 DELTA는 리뷰하지 않는다.
- 전체 브랜치 리뷰(opus)는 **문서 DELTA 전, 병합 전**에 한다. 결함이 나오면 문서를 쓰기 전에 고친다.
  diff·log 범위는 `<착수 커밋>..HEAD`로 고정한다(`_meta.md`의 착수 커밋) — `dev..HEAD`나 푸시하지
  않은 커밋 전체가 아니라 이 작업에서 만든 커밋만 리뷰 대상으로 삼는다.
- 리뷰 지적이 기록·문서 서술의 Minor뿐이면 새 DELTA를 만들지 않는다. 오케스트레이터가 바로 고쳐 같은
  DELTA 커밋에 넣거나, 판단에 영향이 없으면 버린다.

## 이어받기 (다른 에이전트가 이어서 진행)

새 에이전트는 대화 맥락 없이 작업 폴더 경로만 받을 수 있다. 다음 순서로 상태를 복원한다.

1. `_meta.md`를 읽는다. `상태: 완료`면 더 할 일이 없다 — 사용자에게 보고하고 멈춘다.
2. `git switch <작업 브랜치>`로 전환한다. 브랜치가 없으면 사용자에게 보고하고 멈춘다 —
   추측해서 새로 만들지 않는다.
3. `checklist.md`를 읽어 목표·범위·완료 조건·DELTA 목록(체크 상태)을 파악한다.
4. 존재하는 `DELTA-NN.md`를 번호 순으로 읽는다. "## 결과"가 채워져 있으면 그 DELTA는
   완료된 것이다. **마지막 파일의 "## 결과"가 비어 있거나 그 DELTA 파일 자체가 아직
   없으면, 그 DELTA가 진행 중(또는 미시작)이라는 뜻** — 이어서 그 DELTA부터 계속한다.
5. 각 `DELTA-NN.md`의 "## 결정"(있으면)을 읽어 이미 내린 판단과 근거를 파악한다. 같은
   판단을 다시 하지 않는다.
6. `pending-traps/`, `pending-issues/`에 이미 있는 임시 기록은 그대로 두고 이어서
   추가한다 — 마무리 시점 전까지 승격 여부를 판단하지 않는다.

무엇이 없거나 애매하면(브랜치가 없다, `_meta.md`가 없다, 마지막 DELTA 파일에 계획과 결과
둘 다 비어 있다 등) 추측해서 진행하지 않고 사용자에게 보고한다.

## 브랜치와 병합

- 작업 브랜치는 항상 `dev`에서 분기한다.
- 브랜치 이름은 작업 폴더의 `<제목>`(날짜 접두어 제외). 예: `example-task`.
- DELTA 진행 중에는 이 브랜치에 필요한 만큼 자유롭게 커밋한다 — `main`이 아니라 작업
  브랜치이므로 매 커밋 확인은 받지 않는다.
- checklist를 다 채우면 `dev`로 병합하기 전에 커밋을 의미 단위로 재그룹화해 커밋 수를
  줄인다(아래 "재그룹화"). 병합은 `dev`에 `git merge --ff-only`로만 한다.
- `main`으로의 병합·rebase·push는 하지 않는다. `main` 작업은 사용자가 별도로 지시한다.
- 작업 브랜치의 커밋 해시는 재그룹화로 바뀔 수 있다 — `dev`로 병합되기 전까지 checklist·
  DELTA 문서·이슈 초안에 해시를 적지 않는다. 참조는 파일 경로·DELTA 번호·테스트 이름으로
  한다.

### 재그룹화

`git rebase -i`는 쓰지 않는다 — 에이전트 세션은 `GIT_EDITOR`가 비대화형이라 아무것도
합치지 않은 채 "Successfully rebased"를 반환할 수 있다(`GIT_SEQUENCE_EDITOR` 우회도
마찬가지). 대신:

1. 백업 ref를 남긴다: `git update-ref refs/backup/<브랜치>-pre-squash HEAD`
2. `git log --oneline --name-only dev..HEAD`로 의미 단위 그룹을 정한다.
3. `git switch --detach dev` 후 그룹별로 `git cherry-pick -n <커밋...>`과
   `git commit -m "..."`을 반복한다.
4. `git diff refs/backup/<브랜치>-pre-squash HEAD --stat`로 트리가 같은지 대조한다(의도적
   으로 버린 커밋이 없다면 빈 출력).
5. `git branch -f <브랜치> HEAD` 후 `git switch dev && git merge --ff-only <브랜치>`.
6. 병합 후 백업 ref를 지운다: `git update-ref -d refs/backup/<브랜치>-pre-squash`
7. 작업 브랜치를 삭제한다: `git branch -d <브랜치>`

커밋 메시지는 한글, 컨벤셔널 커밋(`feat:`/`fix:`/`refactor:`/`style:`/`docs:`/`test:`/`chore:`
등)으로 쓰고, `claude`, `Generated with`, `Co-Authored-By`, `Claude-Session` 문구를 넣지 않는다.

## 마무리

checklist의 완료 조건을 전부 만족하면:

1. 작업 중 확정한 설계 규칙 중 장기 문서화가 필요한 것을 `docs/design/`에 등록한다(아래
   "설계 결정 → docs/design 등록").
2. `pending-traps/`, `pending-issues/`를 훑어 승격 여부를 판단한다(아래 기준).
3. ROADMAP.md 항목에서 시작한 작업이면 `ROADMAP.md`에서 해당 항목을 완료로 표시한다.
   브레인스토밍에서 시작한 작업이면 이 단계는 없다.
4. "브랜치와 병합"에 따라 재그룹화 후 `dev`에 병합한다.
5. `_meta.md`의 `상태`를 `완료`로 바꾼다.
6. 작업 폴더를 `_works/_completed/<원래 폴더명>/`으로 옮긴다(`mv`, 이름은 그대로 —
   이미 `yyyyMMdd-NN-<제목>` 형식이라 재명명하지 않는다). `_works/`가 통째로 gitignore
   대상이라 이 이동은 git에 기록되지 않는다.

### 설계 결정 → docs/design 등록

작업 중 확정한 설계 규칙(판정 조건·상태표·프로토콜·상수 등 다음에도 참고할 값)은
`_works/`에만 남기지 않는다 — `_works/`는 gitignore 대상이라 병합 뒤에도 git에 남지
않는다. 소유 모듈의 `docs/design/*.md` 절에 적고(위 "문서 갱신: 규칙은 한 곳에"), 결정의
배경·검토한 대안처럼 "왜"에 해당하는 것만 `docs/adr/`에 남긴다. checklist·`DELTA-NN.md`의
"## 결정"은 작업 중 판단을 남기는 임시 기록이지 장기 문서가 아니다 — 병합 전에 옮긴다.

### 함정 → 장기 문서화

모두 만족해야 승격: (1) 다시 겪을 조건을 특정할 수 있다 (2) 성공한 것처럼 보이는 신호가
있어 조용히 넘어갈 위험이 있다 (3) 재발 가능성이 있다.

승격하면 `docs/traps/`에 `INDEX.md` + `TRP-NNN-<slug>.md`(3자리, 001부터, 삭제한 ID 재사용
안 함) 형식으로 기록한다. 처음 승격할 때 디렉터리와 `INDEX.md`를 만든다. 승격 문서는 추적
문서이므로 `_works/` 경로와 DELTA 번호를 적지 않는다.

```markdown
# TRP-NNN <제목>

- 상태: ACTIVE
- 적용 조건: <무엇을 할 때 해당하는지>

## 오해하기 쉬운 신호

## 원인

## 탐지/회피
```

승격하지 않으면 그 작업 폴더의 `pending-traps/`에만 남고 자연 소멸한다.

### 후속 작업 → 등록

- 현재 ROADMAP.md 항목의 범위 안이면 그 항목의 하위 항목으로 `ROADMAP.md`에 삽입한다
  (`ROADMAP.md` 작성 전에는 이 경로가 없다).
- 범위 밖이거나 ROADMAP.md와 무관한 작업(브레인스토밍 시작, `ROADMAP.md` 작성 전 포함)이면
  GitHub 이슈로 등록한다(`docs/agents/issue-tracker.md`).
- 등록 여부와 상태(open 유지 / `deferred` 라벨)는 `docs/agents/issue-tracker.md` "등록·분류 기준"으로
  정한다 — 사소하면 버려도 된다. 1회 관찰·원인 불명 간헐 실패는 `deferred` 라벨만 붙이고 이 작업에서
  조사하지 않는다.

## 금지

- `git rebase -i`, `GIT_SEQUENCE_EDITOR` 우회
- 재그룹화 없이 `dev`에 병합(커밋이 그대로 늘어나는 것 방지)
- `main`을 대상으로 하는 merge, rebase, push
- `git reset --hard`, force push, 광범위한 `git clean`
