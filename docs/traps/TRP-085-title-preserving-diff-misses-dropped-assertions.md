# TRP-085 시험 제목이 그대로면 diff는 "단언이 대체 없이 빠짐"을 못 잡는다

- 상태: ACTIVE
- 적용 조건: 가짜 core/가짜 사건을 실제 사건으로 옮기는 시험 전환(seam 삭제류)에서, 시나리오를 만드는 코드를 지우면서
  뒤따르는 assertion은 손대지 않고 "지운 시나리오가 만들던 조건"만 조용히 사라질 때.

## 오해하기 쉬운 신호

- `vitest list --json` 제목 집합 대조(삭제 D·이름 변경 N 판정)가 **통과**한다 — 시험 제목이 그대로라 겉보기엔 문제가
  없다. 실제로는 검증 대상(예: "running 상태에서도 X가 일어나지 않는다")이 사라지고 다른 상태(예: `ready`)와 우연히
  같은 겉모습만 남는다.
- 시험이 그대로 통과한다. assertion 자체는 정상 실행되고 실패하지 않는다 — 다만 원래 잡으려던 결함을 더 이상 잡지
  못할 뿐이다.

## 원인

시나리오 구성 코드(예: `core.setStatus("running")` 직접 주입)를 실제 사건(예: `handle.run(code)`)으로 바꾸는 리팩터에서,
그 시나리오가 만들던 전제 조건을 재현할 손잡이가 실제 core에는 없을 수 있다. 이때 assertion을 지우거나 약화시키면서
시험 제목·나머지 assertion은 그대로 두면, 제목 기반 diff·이름 집합 대조로는 이 축소를 검출할 수 없다.

관찰된 사례(RD-031, `packages/pyodide-terminal/src/terminal-runner.test.ts`):

- "runner를 dispose하고 Readline을 떼되 Terminal은 dispose하지 않는다" 시험이 `core.setStatus("running")` 직접 주입을
  대체 없이 빼먹어, "running 상태에서도 dispose가 Ctrl+C 핸들러를 뗀다"는 검증 대상을 잃었다(`ready` 상태의 무동작과
  우연히 같은 결과라 통과했다).
- `[C2]` 시험 2건이 "입력 취소 → `^C`를 쓰지 않는다"는 화면 조건(`expect(screen()).not.toContain("^C")`)을 단언하지
  않은 채 메일박스·signal만 확인해, `!== "ignored"`(대신 `=== "sent"`가 아닌) 한 토큰짜리 변이가 살아남았다.
- 벤더 읽기 취소 시험과 `[C2]` "읽기가 그려지기 전" 시험이 옛 `core.calls.interrupt` 0/1 단언을 `worker().signal() === 0`으로
  바꿔, 두 경로가 같은 관찰(signal 0·메일박스 CANCELLED·`^C` 없음)이 되어 서로 바꿔 넣어도 통과했다. 옛 단언이 가르던
  **경로**는 전제 단언(키가 그려지는가 = 벤더에 활성 읽기가 있는가)으로 따로 세워야 했다.

## 탐지/회피

- 시험 전환 리뷰에서 "이름 집합 대조 통과"에 의존하지 말고, 지워진 시나리오 구성 코드가 있으면 그 코드가 만들던
  **조건**이 남은 코드(또는 대체 코드)로 여전히 성립하는지 diff를 줄 단위로 대조한다.
- 시나리오를 옮긴 시험마다, 원래 assertion 목록과 새 assertion 목록을 1:1로 대조해 빠진 것이 있는지 확인한다.
- 의심스러운 assertion 축소가 있으면 그 규칙을 깨는 한 토큰짜리 변이(부정 연산자 뒤집기, 조건 값 하나 바꾸기)를
  스크래치에서 넣어 실제로 killed되는지 돌려 본다.
