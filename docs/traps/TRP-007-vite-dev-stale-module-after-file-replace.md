# TRP-007 파일을 `git checkout`으로 되돌린 뒤 다시 변조하면 vite dev가 낡은 모듈을 계속 준다

- 상태: ACTIVE
- 적용 조건: vite dev 서버를 띄워 둔 채 워크스페이스 소스 파일을 변조 → `git checkout -- <파일>`로 원복 → 다시 변조하며 브라우저 확인을 반복할 때(양성 대조, 브라우저 변이 검사). 서버를 재시작하지 않는다. `git stash`·`git show <커밋>:<파일> > <파일>`·스크립트 쓰기로 소스를 바꾼 뒤 같은 서버로 브라우저 확인·프로브를 돌릴 때도 같다(수정 전·후 비교, 아래 확장).

## 오해하기 쉬운 신호

- 변조가 디스크에 들어갔고 원복 뒤 `git diff --quiet`도 깨끗하다. 브라우저 확인은 전부 통과한다. "변조해도 통과한다"가 시험 구멍이나 아무것도 검사하지 않는 스크립트로 읽힌다.
- 두 번째 변조 실행이 첫 번째와 다르게 전부 통과한다. 원복 뒤 재실행이 통과하는 것과 구분되지 않는다.

## 원인

`git checkout`은 파일을 새 inode로 교체한다. vite의 파일 감시가 교체된 파일을 놓쳐 이후 변경이 모듈 그래프를 무효화하지 않고, dev 서버가 낡은 변환 결과를 준다. 디스크에는 `sinks.resetTail();` 줄이 0개인데 `curl http://localhost:5173/@fs/<절대경로>/repl-reader.ts`는 1개짜리 모듈을 돌려줬다.

## 탐지/회피

- 회피: 변조를 적용한 뒤와 원복한 뒤에 각각 dev 서버를 재시작한다(2초 안팎). 재시작하지 않는 양성 대조 결과는 신뢰하지 않는다.
- 탐지: 변조 뒤 `curl -s http://localhost:5173/@fs/<절대경로>/<파일> | grep`으로 서버가 주는 모듈에 변조가 보이는지 본다. 실패해야 하는 확인이 통과하면 이 원인을 먼저 의심한다.

## 확장(RD-022)

- 원복(`git checkout`)만이 아니라 `git stash`·`git show <커밋>:<파일> > <파일>`·스크립트 쓰기로 소스를 교체한 뒤에도 같은 서버가 교체를 반영하지 않는 경우가 있었다(이 WSL 저장소 경로, 서버가 모듈을 처음 서빙한 뒤의 변경). 수정 전 코드로 되돌렸는데 결함이 재현되지 않거나, 수정 후 결과가 수정과 무관하게 같으면 수정 여부를 판정하는 실행이 옛 코드(또는 임시 디버그 훅이 든 코드)로 돈 것이다.
- 회피: 코드 상태를 바꾼 뒤마다 서버를 재시작하고(`lsof -ti tcp:5173 | xargs kill` 뒤 다시 기동) `curl`로 서빙 본문에 바뀐 줄이 있는지 확인한 다음 브라우저 확인을 돌린다. 판정 근거에는 재시작 뒤 실행만 쓴다.
