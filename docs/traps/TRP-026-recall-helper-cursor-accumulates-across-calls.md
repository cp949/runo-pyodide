# TRP-026 한 시험 안에서 history 재호출 도우미를 연달아 부르면 cursor가 누적돼 변이를 가린다

- 상태: ACTIVE
- 적용 조건: 벤더 `Readline`이 `read()` 시작 시 `history.cursor`를 리셋하지 않는(`append()`/`restore()`에서만
  리셋) 성질에 의존해 ↑ 재호출로 history를 관찰하는 시험 하니스에서, 한 시험 안에 재호출 도우미(예:
  `recall(n)`)를 2회 이상 연달아 부를 때.

## 오해하기 쉬운 신호

- 시험이 그린으로 통과한다. 겉보기엔 정상이다.
- 실제로는 entries가 어긋나 있는데도(예: 변이로 복원 로직이 빠진 상태) 두 번째 호출부터 누적된 cursor
  오프셋이 그 어긋남과 우연히 상쇄돼 같은 기대값을 돌려준다 — 변이 검사에서 "SURVIVED"로만 드러난다.
- 시험을 코드만 읽고 리뷰하면 "재호출을 두 번 하니 항목 두 개를 각각 확인한다"로 보여 문제를 못 찾는다.

## 원인

`Readline`은 `read()`가 새 읽기를 시작해도 `history.cursor`를 초기화하지 않는다. cursor는 `append()`(제출)나
`restore()`(복원)가 부를 때만 리셋된다. 한 시험 함수 안에서 "↑로 n번째 이전 항목을 본다"는 도우미를
제출·취소 없이 연달아 부르면, 두 번째 호출의 cursor는 첫 호출이 남긴 위치에서 이어 움직인다 — entries 배열
자체가 변이로 인해 한 칸 어긋나 있어도, 관찰 시점의 cursor도 같이 한 칸 밀려 있으면 두 어긋남이 상쇄돼
기대한 문자열이 그대로 나온다.

## 탐지/회피

- 재호출 도우미를 한 시험 안에서 2회 이상 부를 때는 그 사이에 `entries.length`나 특정 인덱스의 값을 직접
  단언하는 시험을 별도로 추가해, cursor 누적으로 가려지는 어긋남을 잡는다(`entries` 직접 단언은 ↑로 구분할
  수 없는 경우—50개 제한 복구, 중복 제거 복구 등—에 한정해서 쓴다).
- 변이 검사를 새 시험 스위트에 적용할 때 "SURVIVED"가 나오면, 재호출 도우미의 연쇄 호출부터 cursor 누적을
  의심한다. 시험을 다시 쓰기보다(하니스 버그가 아니라 관찰 맹점이므로) entries 직접 단언을 보강하는 쪽을
  먼저 시도한다.
- 재현: `Readline`으로 `append("a")`·`append("if True:")`·`append("b")` 뒤 ↑를 두 번 눌러 `"if True:"`를 본
  상태에서(cursor가 남아 있다), 그다음 변이로 entries가 `["b","if True:","a"]`가 아니라 어긋난 상태에서도
  같은 코드로 다시 ↑ 재호출을 하면 cursor 누적 때문에 기대값과 우연히 일치할 수 있다(`block-history.test.ts`
  DELTA-03 리뷰에서 실측).
