# TRP-032 pty로 "실행 중 친 키"를 재면 tty가 먼저 해석해 프롬프트 화면 비교가 조용히 어긋난다

- 상태: ACTIVE
- 적용 조건: 3.14 REPL을 pty로 띄워 **실행 중**(`time.sleep` 등, 프롬프트가 없는 구간)에 키를 보내고 종료 뒤 프롬프트를 웹과 대조할 때. 방향키·Ctrl+D 같은 제어 키를 pty에 흘릴 때. 기준 데이터는 `apps/demo/e2e/pty/rd-019/`.

## 오해하기 쉬운 신호

- 오류가 없고 화면이 그럴듯하다. 아래는 모두 "웹과 같아 보이거나 무동작처럼 보이는" 형태로 나온다.
- **에코 접두**: 실행 중 cooked 모드 tty가 입력을 에코한다(`abc`, Enter `\r\n`, Backspace·Ctrl+U `\b \b`, ESC `^[`, Ctrl+C `^C`). 프롬프트가 그 행 뒤에 이어 붙어 `abc>>> abc`가 된다. 절대 행 문자열·열로 웹(`>>> abc`, 열 7)과 비교하면 항상 다르다. 에코를 뺀 프롬프트 부분과 프롬프트 시작 기준 열로 비교한다.
- **`ESC[D`와 `ESC O D`는 다르다**: 실행 중 터미널은 일반 커서 키 모드(`\x1b[?1l`)라 `ESC[D`를 보내는데, 프롬프트의 `_pyrepl`은 애플리케이션 모드(`\x1b[?1h`)의 `ESC O D`만 왼쪽으로 안다. `ESC[D`는 버려지고 뒤따른 글자까지 사라진다(`ab` `ESC[D` `c` → `>>> ab`). "←가 무동작"으로 오인하기 쉽다. 화살표를 pty에 흘리는 시험은 어느 쪽을 보냈는지 적는다.
- **Ctrl+D는 EOF가 아니다**: cooked 모드의 `0x04`는 NUL 한 개가 되어 `_pyrepl` 입력줄에 폭 0 글자로 들어간다. 화면은 무동작이고 REPL도 종료하지 않는다. Enter로 제출해야 `SyntaxError: source code string cannot contain null bytes`로 드러난다. 이는 **실행 중**(프롬프트가 없는 구간)에 친 키가 tty를 거치는 경우다 — 프롬프트가 열려 실제로 친 빈 입력줄의 Ctrl+D를 EOF로 처리하는 웹 규칙은 별개다(`docs/design/06-editing.md` 6.9).
- **바이트 조각 경계가 실행마다 다르다**: "종료 뒤 프롬프트"와 "프롬프트 뒤 잔여" 두 읽기 사이의 경계(예: `\x1b[1@` 위치)가 타이밍에 따라 달라진다. 조각별로 비교하면 같은 시나리오가 실행마다 다르게 보인다.
- 화면 해석기가 모르는 시퀀스는 조용히 무시된다. 한 줄이 80열을 넘는 입력(수천 자)은 재그리기가 CUP(`ESC[행;열H`)를 내 최소 해석기가 못 다룬다.

## 원인

실행 중에는 파이썬이 아니라 tty 라인 디시플린(cooked, `ECHO`·`ICANON`·`ISIG`)이 입력을 먼저 해석한다. `_pyrepl`은 프롬프트를 다시 그릴 때 raw 모드로 바꾸면서 큐에 쌓인 바이트를 읽는다. 그래서 큐에는 tty가 지우거나 바꾼 결과만 남고, 에코는 출력 행에 이미 찍혀 있다. 입력 큐는 한 줄 4095자로 잘린다(웹 상한과 다름, `docs/design/10-parity-deviations.md` 49).

## 탐지/회피

- 비교는 두 단계를 합친 화면 해석으로만 하고 에코 접두를 뺀 프롬프트 부분·프롬프트 시작 기준 열을 쓴다.
- 제어 키는 Enter로 제출해 실제 버퍼를 확인한다(NUL·버려진 글자는 화면만으로 안 보인다).
- 화살표 시험은 `ESC[D`(실행 중 터미널이 보내는 형태)와 `ESC O D`(애플리케이션 모드)를 둘 다 시험해 원인을 가른다.
- 새 시나리오에서 해석기의 `unhandled` 목록이 비어 있는지 먼저 본다(`apps/demo/e2e/pty/rd-019/pty_type_ahead.py`, 재현 `python3 apps/demo/e2e/pty/rd-019/pty_type_ahead.py`).
