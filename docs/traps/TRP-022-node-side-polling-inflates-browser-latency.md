# TRP-022 브라우저 지연을 Node 쪽 폴링으로 재면 문턱 근처에서 5~8ms 과대 측정된다

- 상태: ACTIVE
- 적용 조건: Playwright 하니스가 "키 입력 → 화면 변화" 지연을 재고 판정선이 수십 ms일 때. 특히 `keyboard.press` 직전 **Node** `performance.now()`를 찍고 `page.$$eval`류 호출로 화면을 폴링해 변화 시각을 잡는 방식.

## 오해하기 쉬운 신호

- 측정 자체는 **완주한다**. 240시행이 전부 돌고 셀별 중앙값·최대가 그럴싸한 분포로 나온다.
- 결과가 판정선을 **살짝** 넘는다(실측: 12셀 중 8셀 중앙값 31.5~33.9ms, 문턱 30ms). 여러 셀이 일관되게 넘어 우연이나 잡음으로 보이지 않고, "구현이 문턱을 못 맞춘다"는 결론이 자연스럽게 나온다.
- 같은 코드의 node 프로세스 내부 측정은 sub-30ms인데, 브라우저가 더 느린 것으로 설명해 버리기 쉽다.

## 원인

눌림 시각은 Node 시계에서 찍고, 화면 변화 시각은 **Node가 관측한 시각**이다. 폴링 주기마다 Node↔Chromium CDP 왕복이 최소 2회 끼어 그 왕복 지연이 측정값에 그대로 더해진다(실측 평균 +5~8ms). 폴링 간격을 줄여도 왕복은 줄지 않는다.

폴링 루프 1회 안에서 DOM 조회를 여러 번 하면 과대 측정이 폴링 간격이 아니라 **조회 횟수 × 왕복 지연**으로 커진다. 사례: `input-cancel-check.mjs` EC(Ctrl+C → `KeyboardInterrupt` 출현)는 수정 전에 25ms 간격 루프의 매 회 `countOf()`를 2번(`loop-done`·`KeyboardInterrupt`) 불러, `waitForTimeout(25)` 대기와 별개로 CDP 왕복 2회 이상이 값에 섞였다. 같은 조건(`E2E_CPU_THROTTLE=4`)에서 Node 시계 44ms가 페이지 시계로 바꾼 뒤 33.3ms였다(정상 속도 25.2ms). 차이는 측정법 몫이지 성능 개선이 아니므로 두 값을 이어 비교하지 않는다. 판정선이 수백 ms인 상한(1000ms)에서는 결과를 바꾸지 않지만 문턱이 수십 ms이면 위 신호가 그대로 나타난다.

## 탐지/회피

- 두 시각을 **모두 페이지 안에서** 잡는다: 페이지 내부 keydown 리스너와 `MutationObserver`가 같은 `performance.now()` 시계로 기록하고, Node는 끝난 뒤 값만 읽는다. Node↔페이지 시계 오프셋 문제 자체가 없어진다.
- "무엇을 재는가"(눌림 시각 → 새 프롬프트가 보인 시각)는 바꾸지 않는다. 바뀌는 것은 "어느 시계로 재는가"뿐이다 — 측정 대상을 함께 바꾸면 이전 결과와 대조할 수 없다.
- 문턱 근처 결과는 **다른 시계로 한 번 더 재기 전에** 회귀로 보고하지 않는다. 판정선에서 5~10ms 안쪽이면 측정법부터 의심한다.
- 출현 시각은 `lib.mjs`의 `markText(pattern, { exclude, startOnKey })` / `readMark()`로 잡는다(페이지 안 `MutationObserver`, 시작은 `keydown` 캡처의 페이지 시각). 제출한 소스 줄이 대상 문자열을 담으면 즉시 참이 되므로 `exclude`로 소스 줄을 거른다(TRP-011). 폴링 루프 안에서 조회를 여러 번 하지 않는다.
- 지연 자체를 재지 않고 "복귀했다/안 했다"만 보는 확인에는 이 정밀도가 필요 없다 — 폴링 방식을 그대로 써도 된다.
- 페이지 밖 시계는 지연 판정에 섞지 않는다. 2026-09-25 Chromium(WSL2) 측정에서 같은 8초 호출의 Python `time.time()` 경과가 main `performance.now()`와 달리 약 10.9~11.4초로 나온 회가 40회 중 11회였고(main 시계는 8001~8006ms), Node `Date.now()`와 페이지 `performance.timeOrigin + performance.now()`를 빼면 한 실행 안에서 약 3.3초 어긋난 구간이 있었다. 원인은 확인하지 않았다(벽시계 조정 추정). Python 안 시계·Node 시계 값은 표·판정에 쓰지 않는다.
- 실패한 1차 측정 로그를 버리지 않는다. 측정법을 바꾼 판단이 틀렸을 때 되돌릴 근거가 된다.
