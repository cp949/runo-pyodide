# 양성 대조(DELTA-05)

브라우저 확인이 실제로 `packages/pyodide-repl/src/terminal/block-history.ts`의 배선을 보는지, 세 지점을
차례로 임시로 망가뜨려 실패를 확인한 뒤 원복했다. `pnpm --filter demo dev`는 vite dev의 `development`
export 조건(TRP-001)을 쓰므로 소스를 고친 뒤 **서버를 재시작**해야 반영된다(RD-013 positive-controls.md와
같은 이유).

절차마다: ① 편집 → ② 기존 dev 프로세스 kill 후 재기동 → ③ 대상 절 실행(`ONLY=`) → ④ 실패 확인 →
⑤ `git diff --stat`으로 원복 확인(대상 파일 1개만) → ⑥ `git checkout --`로 원복 → ⑦ 서버 재기동 →
⑧ 전체 29개 재확인(GREEN).

## 양성 대조 ①: `historyEntry`에서 `restore(blockBase)`를 뺀다

`historyEntry(line)`에서 `history.restore(blockBase);` 한 줄을 제거하고 곧바로
`` `${pendingBlock}\n${line}`.trimEnd() `` 만 반환하게 했다.

결과(`ONLY="초기,A,B"`, 8개 중 7개 통과):

- 실패(1): `A A2`(↑를 한 번 더 누르면 줄 조각이 아니라 블록 이전 항목이 나온다) — 기대
  `[">>> x = 1"]` 대신 `[">>> for i in range(2):"]`(블록 항목이 중복 누적되어 두 번째 ↑도 같은
  블록 조각을 반환). 계획 문구와 일치.
- 통과(오탐 아님 — 이 변이로는 안 죽는다): `B B2`(취소한 블록은 남지 않는다). **계획
  문구("A2·B2 실패 예상")와 달리 `B2`는 이 변이로 죽지 않는다** — `discard()`가
  `historyEntry`와 별개로 자기 `blockBase`를 직접 `getHistory().restore()`하므로, 취소
  경로는 `historyEntry`의 `restore` 누락과 무관하게 항상 정상 복원된다(DELTA-03 "발견/처리"의
  M1 분석과 정확히 같은 이유 — 코드 확인: `block-history.ts`의 `discard()`는
  `readline.getHistory().restore(blockBase)`를 자체적으로 부른다). 브라우저 확인은 취소 경로가
  아니라 재호출(↑) 경로에서만 이 변이를 잡는다.

`git diff --stat`: `packages/pyodide-repl/src/terminal/block-history.ts | 1 -`(대상 파일만).

## 양성 대조 ②: `trimEnd()`를 뺀다

`` `${pendingBlock}\n${line}`.trimEnd() ``에서 `.trimEnd()`를 제거했다.

결과: **계획이 예상한 `A1` 또는 `I1`은 물론, 추가로 시도한 Shift+Enter 뒤 빈 둘째 줄 제출
시나리오(단위 시험 16번과 같은 모양)까지 전부 이 변이로 죽지 않는다(브라우저 확인 전체 29개

- 추가 시나리오 1개, 총 3가지 시도 모두 GREEN 그대로).**

시도한 경로:

1. `ONLY="초기,A"`(A1: `>>> for i in range(2):` / `    print(i)` 재호출) — 통과(안 죽음). A1의
   마지막 `historyEntry` 호출은 `"    print(i)"`(빈 줄 제출은 `skipBlankHistory`가 걸러
   `historyEntry` 자체가 안 불린다) — 애초에 끝 공백이 없는 문자열이라 `trimEnd()` 유무가
   결과에 차이를 만들지 않는다.
2. `ONLY="초기,...,I"`(I1: Shift+Enter로 `print(1)`/`print(2)` 둘 다 실제 코드를 채운 뒤 제출) —
   통과(안 죽음). 마찬가지로 제출된 텍스트 끝에 공백이 없다.
3. 추가 시나리오(디버그 스크립트, 단위 시험 16번을 흉내냄): `if True:` → `... ` `print(1)` +
   Shift+Enter(둘째 줄은 프리필만, 직접 타이핑 없음) + Enter로 그대로 제출. 이번엔 제출된
   텍스트가 `"print(1)\n    "`(끝에 프리필 공백)로 **끝 공백이 실제로 있다** — `trimEnd()`가
   있고 없고의 차이가 소스 레벨에서는 분명히 존재한다. 그런데도 화면에서는 구분되지 않았다:
   `lib.mjs`의 `rows()`가 각 행을 `.replace(/\s+$/, "")`(행별 끝 공백 제거)로 읽기 때문에, 끝
   공백만 있는 "셋째 행"이 애초에 화면에 빈 문자열로도 안 나타난다(`tail(4)`가 2행만 반환,
   `trimmedRows()`가 끝의 빈 행을 자른다). 즉 **이 하니스는 스크린 텍스트만 읽으므로 순수
   trailing-whitespace 차이를 구조적으로 관찰할 수 없다.**

## 결정

- 양성 대조 ②는 브라우저 스크린 하니스로는 원리적으로 확인 불가능하다(위 "시도한 경로" 3번의
  이유). `trimEnd()` 배선은 이미 단위 시험(`block-history.test.ts` 16번, `recall()`이 문자열
  값을 직접 비교)이 커버하고 변이 검사(`verify/mutations-delta03.json` M2, DELTA-03에서 killed
  확인)로도 확인됐다 — 브라우저 확인이 이 배선을 **추가로** 검증하지는 못한다는 사실만
  기록한다. `block-history-check.mjs`에 새 절을 추가하지 않았다(추가해도 항상 통과하는
  무의미한 검사가 된다). 계획서(DELTA-05.md)의 "A1 또는 I1 실패 예상(실측으로 확정)" 문구는
  소급 수정하지 않는다(rubber-workflow 관례, RD-013 positive-controls.md와 동일).
- 양성 대조 ①은 계획이 예상한 두 실패(A2·B2) 중 A2만 재현됐다. 원인은 DELTA-03이 이미 M1에서
  같은 이유로 문서화한 것과 동일하다(`discard()`의 독립적 복원). 계획 문구를 소급 수정하지
  않고 여기 실측을 남긴다.

## 양성 대조 ③: `onKey`의 ↑ 삼킴을 뺀다

`onKey`를 `(input: Input): boolean => false`로 바꿔 항상 미소비로 만들었다.

결과(`ONLY="초기,C"`, 4개 중 2개 실패):

- 실패(2, 계획과 일치): `C C1`(프리필이 없는 `... ` 줄에서 ↑는 history를 탐색하지 않는다) —
  기대 `"..."` 대신 `"... x = ["`(history가 탐색돼 이전 미완성 줄이 프리필된다). `C C2`(프리필을
  지운 `... ` 줄에서도 ↑는 history를 탐색하지 않는다) — 기대 `"..."` 대신 `"... if True:"`.
- 통과(오탐 아님): `C C3`(취소 뒤 `>>> `의 ↑는 다시 탐색한다) — `>>> ` 프롬프트는 애초에 ↑
  삼킴 대상이 아니므로(onKey는 `... ` 줄에서만 관여) 이 변이와 무관하게 항상 통과한다.

`git diff --stat`: `packages/pyodide-repl/src/terminal/block-history.ts | 5 +----`(대상 파일만).
