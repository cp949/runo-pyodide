# RD-019 양성 대조 (DELTA-02, 브라우저 1건)

`checks/type-ahead-check.mjs`가 실제로 "읽기가 없는 구간에 친 키의 재생"을 검출하는지, 벤더 재생 호출을 제거한 변이로
`sleep` 셀(T01)이 실패하는지 확인했다. 검출력 근거는 두 곳에 나뉜다: (1) 벤더 단위 시험 16건과 변이 검사 14/14(L0,
`packages/xterm-readline/src/type-ahead.test.ts`) (2) 이 브라우저 대조(대상 셀 1개). 단위 변이는 이 문서 범위가 아니다.

`pnpm --filter demo dev`는 vite dev의 `development` export 조건으로 워크스페이스 소스를 그대로 읽는다. 소스를 고친 뒤 **서버를
재시작**해야 반영된다(TRP-007). 깨끗한 트리에서 시작한다(`git status --short`에 대상 파일이 없어야 한다).

## 대조: `read()` write 콜백의 `replayTypeAhead()` 호출 제거

- 변경: `packages/xterm-readline/src/readline.ts`의 `read()` write 콜백 끝
  `this.replayTypeAhead();`를 주석 처리했다. 키는 여전히 `typeAhead`에 쌓이지만 다음 읽기가 시작돼도 재생되지 않는다.
  (`sed -i 's|^        this.replayTypeAhead();$|        // this.replayTypeAhead();|' packages/xterm-readline/src/readline.ts`)
- 절차: 편집 → dev 서버 kill 후 재기동(`pnpm --filter demo dev`) → `ONLY=T01 node e2e/checks/type-ahead-check.mjs` → 실패 확인 →
  `git checkout -- packages/xterm-readline/src/readline.ts` → dev 재시작 → 같은 명령 재실행 → 통과 확인.
- 변이 상태 실행 결과(`ONLY=T01`, 2개 중 1개 실패, 22.4초):
  ```
  PASS  초기: 프롬프트가 뜬다
  FAIL  T01 실행 중 `abc` → 종료 뒤 마지막 행 `>>> abc`, 커서가 그 끝  — 시간 초과: 프롬프트 ">>> abc"
        — 화면 끝 [">>> import time; print('RUN01'); time.sleep(2)","RUN01",">>>"]
  ```
  실행이 끝난 뒤 프롬프트는 `>>>`뿐이라 쌓인 `abc`가 재생되지 않은 것이 그대로 보인다.
- 원복 뒤 결과(`ONLY=T01`, 2/2 통과, 4.4초). 원복은 `git status --short`로 변이 대상 파일이 사라진 것을 확인했다.
- 로그: `_works/20260924-22-rd-019-type-ahead/verify/delta02-positive-control-mutated.log`,
  `delta02-positive-control-restored.log`.

## 재현 시 주의

- 전 셀을 돌릴 때 T08(부팅 중 키)은 `open()` 직후 `status`가 `loading`인 동안 친다. 부팅이 이미 끝난 상태(캐시가 극단적으로 빠른
  경우)면 시나리오 전제가 성립하지 않아 T08이 전제 오류로 실패한다(오류 메시지에 `status` 값이 담긴다).
- T04(Enter 직후 지연 0ms)는 수정 전 0ms 유입이 1/10이라 이 셀 하나의 회귀 검출력은 약 90%다. 결정적 검출력은 T01(`sleep` 셀)이
  맡는다.
